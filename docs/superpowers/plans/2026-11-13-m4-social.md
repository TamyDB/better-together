# M4 Social: Plano de Implementação

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Os jogadores conversam por chat de texto e mandam emotes. A mensagem aparece num balão acima do bichinho de quem falou (na overlay do Host e no viewer de cada convidado) e num histórico curto. O emote aparece como um ícone grande acima do bichinho por alguns segundos.

**Architecture:** Chat e emote são mensagens do canal `events` (confiável e ordenado). O convidado manda `GuestMsg::Chat`/`GuestMsg::Emote`; o Host valida (jogador admitido, texto sanitizado, limite por jogador), carimba o autor e repassa `HostMsg::Chat`/`HostMsg::Emote` a todos os convidados admitidos, inclusive ao próprio autor, e à UI local. Ninguém mostra a própria mensagem antes do eco do Host: o Host é a autoridade e o que foi barrado pelo limite não aparece para ninguém. A `sim` não muda (balões são UI). As teclas `1`–`6` viram emotes no Rust (`Key::Emote`), tanto no viewer do convidado quanto no modo bichinho do Host. O TS só desenha balões (canvas `fillText`) e o histórico (`textContent`).

**Tech Stack:** o que já existe no M3. Sem dependências novas.

**Spec:** `docs/superpowers/specs/2026-11-05-desktop-multiplayer-design.md`
**Base:** branch `m3-video` (PR #1). O M3 ainda depende do E2E no Windows; o M4 não toca vídeo nem Win32.

## Global Constraints

- `PROTOCOL_VERSION` continua `1` (nada foi distribuído). As variantes novas entram **no fim** dos enums `GuestMsg`/`HostMsg` (a ordem das variantes é o wire format do bincode).
- Emotes: `enum Emote { Heart, Laugh, Wow, Angry, Music, Question }` (serde lowercase). Teclas `Digit1`..`Digit6` (VK `0x31`..`0x36`) na mesma ordem. Ícones na UI: `❤️ 😂 😮 😠 🎵 ❓`.
- Chat: `MAX_CHAT_CHARS = 120` *chars*. `sanitize_chat` remove controle, invisíveis e marcas bidi (as mesmas regras de `sanitize_name`), junta espaços, faz `trim`, corta em 120 chars; vazio → `None`.
- Limites no Host, por jogador e com tempo injetado: chat em token bucket de capacidade 3 com recarga de 1 a cada 2 s; emote com intervalo mínimo de 1 s. Excesso é descartado em silêncio (log debug). O Host também respeita os próprios limites (mesmo código).
- Só jogador admitido (com `player`) fala. Mensagem de peer no lobby, canal errado ou malformada é ignorada.
- O convidado nunca escolhe o autor: o `from` é carimbado pelo Host a partir do peer.
- Balões: emote dura `EMOTE_MS = 2500`; chat dura `CHAT_MS = 5000`; um balão novo do mesmo jogador substitui o anterior do mesmo tipo. Histórico: últimas `LOG_SIZE = 50` mensagens; o viewer mostra as 6 mais recentes.
- Texto vindo de pessoas: no canvas só `fillText`; no DOM só `textContent`.
- Digitar no chat nunca move o bichinho: enquanto o campo tem foco, o viewer não repassa teclas e solta as que estavam pressionadas.
- Textos da UI em português. Workspace compila e testa no Linux.

## Review Focus

1. **Flood e lixo:** convidado manda 100 chats por segundo, texto de 10 mil chars, só espaços, só caracteres invisíveis, RTL override, emote antes do `Hello`. O Host não cai, não repassa nada inválido e respeita os limites. Testes nas Tasks 1 e 2.
2. **Autoria:** um convidado não consegue falar em nome de outro nem do Host. Teste na Task 2.
3. **Teclado:** digitar "wasd 123" no campo do chat não move o bichinho nem dispara emote; `Enter` envia, `Esc` cancela e devolve o controle. Testes na Task 6.
4. **Reconexão e sono:** o pet dormindo pode receber balões dos outros; quem volta pelo rejoin continua falando com o mesmo `PlayerId`. Teste na Task 2.
